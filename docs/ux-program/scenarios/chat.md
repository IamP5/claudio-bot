# Chat scenarios

Generated by `.claude/skills/verify-claudio-bot/bin/scenario.ts doc chat` from `bin/scenarios.ts`; edit the registry, then regenerate. Each scenario answers, for one normal flow, whether the user is told the **state** honestly, can read it **clearly**, gets a **responsive** answer, and knows how to **recover** when something goes wrong.

Lanes: a `protocol` item is judged mechanically from the frames the phone receives (and the run's transcripts, files and pushes as independent views); a `simulator` item is judged by a person or agent from the named screenshots, taken with `--sim`. Every session turn runs on haiku; each permission card the scenario raises is answered Allow once, as the user would, and the timeline records the tap. A scenario whose preconditions fail is reported failed and its rubric is not judged; it never falls back to an easier path.

## C1 A plain message and its reply

Needs the simulator: no (simulator items run with `--sim`).

**User journey.**

1. The user creates a bot and waits for its greeting.
2. They open the chat and send a short message.
3. They watch the bot work and read its reply.
4. They leave and open the chat again.

**Setup.**

- The phone sends a frame the app can send, built from what it saw: create_bot with ref `c1`. Mark `c1-create`.
- Wait up to 15 s for the created reply for `c1`; mark `c1-created`.
- Wait up to 180 s for `c1`'s first turn to end; mark `c1-ready`.
- Open the chat with `c1`: in the app by claudiobot://bot/<id> (simulator lane), or send `open` as the app does (protocol lane). Mark `c1-open`.
- The phone sends a frame the app can send, built from what it saw: send in `c1`: "Reply with one short sentence that contains the word pong.". Mark `c1-send`.
- Wait 2 s.
- Screenshot `c1-working` (simulator lane).
- Wait up to 150 s for `c1`'s reply and the bot at rest; mark `c1-done`.
- Wait 2 s.
- Screenshot `c1-done` (simulator lane).
- Open the chat with `c1`: in the app by claudiobot://bot/<id> (simulator lane), or send `open` as the app does (protocol lane). Mark `c1-reopen`.
- Wait 2 s.

**Preconditions** (any failure fails the scenario):

- bot c1 was created
- the bot replied after the send

**Rubric.**

| id | tells | lane | the user can tell | pass | fail |
| --- | --- | --- | --- | --- | --- |
| C1.1 | responsive | protocol | The message the user sent shows as sent at once. | the bridge echoes the user message with the send's clientId within 1 s | no echo, or it takes over 1 s, so the bubble hangs unconfirmed |
| C1.2 | state | protocol | The bot says it is working soon after the send. | a bot frame with status working within 2 s of the send | no working status, or it comes late, so the chat looks ignored |
| C1.3 | state | protocol | The bot never says it is done before its reply is in. | from the first working status to the last reply, every bot frame says working | an idle status between the send and the reply: the typing row vanishes while the bot still writes |
| C1.4 | state | protocol | When the reply is in, the bot stops saying it is working. | a bot frame with a status other than working arrives within 5 s of the last reply | the bot stays working (Typing…) after its reply, or never says it is done |
| C1.5 | recover | protocol | Opening the chat again shows the same messages. | the conversation that answers the second open holds the user message and the reply | either is missing from the reopened chat |
| C1.6 | state | simulator (c1-working) | While the bot works, the chat shows it: the user's bubble, the typing row and a Stop button. | Typing… under the user's bubble, Stop in place of Send | no typing row, or Send instead of Stop, or the bubble missing |
| C1.7 | clarity | simulator (c1-done) | After the reply, the chat is at rest and the reply reads whole. | the reply in full, no typing row, Send back | a typing row left over, the reply cut, or the composer stuck on Stop |
