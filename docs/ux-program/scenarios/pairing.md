# Pairing scenarios

Generated by `.claude/skills/verify-claudio-bot/bin/scenario.ts doc pairing` from `bin/scenarios.ts`; edit the registry, then regenerate. Each scenario answers, for one normal flow, whether the user is told the **state** honestly, can read it **clearly**, gets a **responsive** answer, and knows how to **recover** when something goes wrong.

Lanes: a `protocol` item is judged mechanically from the frames the phone receives (and the run's transcripts, files and pushes as independent views); a `simulator` item is judged by a person or agent from the named screenshots, taken with `--sim`. Every session turn runs on haiku; each permission card the scenario raises is answered Allow once, as the user would, and the timeline records the tap. A scenario whose preconditions fail is reported failed and its rubric is not judged; it never falls back to an easier path.

## P1 Pair a phone with a code

Needs the simulator: no (simulator items run with `--sim`).

**User journey.**

1. The user reads the pairing code on a paired phone or the Mac.
2. They type it on a new phone, which pairs and connects.
3. Later someone tries the same code again.

**Setup.**

- The phone sends a frame the app can send, built from what it saw: pair_code (Settings, Pair another device). Mark `p1-code`.
- Wait up to 10 s for the pair_code reply; mark `p1-code-in`.
- Another phone, "UX second phone", sends POST /pair with the code; when it pairs it opens a socket with its token and keeps it open. Mark `p1-paired`.
- The phone sends a frame the app can send, built from what it saw: devices. Mark `p1-devices`.
- Wait up to 10 s for the devices reply; mark `p1-devices-in`.
- Another phone, "UX third phone", sends POST /pair with the same code again. Mark `p1-reuse`.

**Preconditions** (any failure fails the scenario):

- the bridge gave a pairing code

**Rubric.**

| id | tells | lane | the user can tell | pass | fail |
| --- | --- | --- | --- | --- | --- |
| P1.1 | clarity | protocol | The code is short to type and says how long it lasts. | eight characters as XXXX-XXXX, an expiry 9 to 11 minutes out, and at least one address | another shape, no expiry, or no address to reach the Mac |
| P1.2 | responsive | protocol | The right code pairs at once and the new phone connects. | POST /pair answers 200 within 2 s and the new socket gets its hello | a refusal, a slow answer, or a socket that never says hello |
| P1.3 | state | protocol | The paired list shows the new phone by its name. | devices lists UX second phone | the new phone is missing |
| P1.4 | recover | protocol | A used code is refused with a reason and the next step. | 401 with a message that says where to get a new code | accepted again, or a refusal that does not say what to do |
| P1.5 | state | simulator (pair-link, after-pairing) | The app pairs from the link and lands on the bot list, connected. | the pairing step, then the list with no error | an error, a blank screen, or a pairing screen left up |

## P2 A mistyped pairing code

Needs the simulator: no (simulator items run with `--sim`).

**User journey.**

1. The user mistypes the code once, then types it right.
2. Later, with a new code, they mistype it five times, then type it right.

**Setup.**

- The phone sends a frame the app can send, built from what it saw: pair_code (Settings, Pair another device). Mark `p2-code`.
- Wait up to 10 s for the pair_code reply; mark `p2-code-in`.
- Another phone, "UX typo phone", sends POST /pair with the code with one character wrong. Mark `p2-typo`.
- Another phone, "UX typo phone", sends POST /pair with the right code. Mark `p2-right`.
- The phone sends a frame the app can send, built from what it saw: pair_code (Settings, Pair another device). Mark `p2-code2`.
- Wait up to 10 s for the pair_code reply; mark `p2-code2-in`.
- Another phone, "UX locked phone", sends POST /pair with the new code with one character wrong (try 1). Mark `p2-wrong1`.
- Another phone, "UX locked phone", sends POST /pair with the new code with one character wrong (try 2). Mark `p2-wrong2`.
- Another phone, "UX locked phone", sends POST /pair with the new code with one character wrong (try 3). Mark `p2-wrong3`.
- Another phone, "UX locked phone", sends POST /pair with the new code with one character wrong (try 4). Mark `p2-wrong4`.
- Another phone, "UX locked phone", sends POST /pair with the new code with one character wrong (try 5). Mark `p2-wrong5`.
- Another phone, "UX locked phone", sends POST /pair with the right new code. Mark `p2-after`.

**Preconditions** (any failure fails the scenario):

- the bridge gave two codes

**Rubric.**

| id | tells | lane | the user can tell | pass | fail |
| --- | --- | --- | --- | --- | --- |
| P2.1 | clarity | protocol | A mistyped code is called wrong. | 401 with a message that says the code is wrong | another status, or a message that blames something else |
| P2.2 | recover | protocol | After one typo, the right code still pairs. | 200 | the typo burned the code |
| P2.3 | recover | protocol | After too many wrong tries, the message says how to go on. | the fifth refusal says where to get a new code | no next step |
| P2.4 | state | protocol | Once locked out, typing the right code is not called wrong. | a refusal that does not say the code is wrong, and says how to go on | the right code is called wrong, or no next step |

## P3 Remove a paired phone

Needs the simulator: no (simulator items run with `--sim`).

**User journey.**

1. The user pairs a second phone.
2. They remove it from Settings, Paired devices.
3. On the simulator lane they also remove the app's own iPhone and look at it.

**Setup.**

- The phone sends a frame the app can send, built from what it saw: pair_code (Settings, Pair another device). Mark `p3-code`.
- Wait up to 10 s for the pair_code reply; mark `p3-code-in`.
- Another phone, "UX second phone", sends POST /pair with the code; when it pairs it opens a socket with its token and keeps it open. Mark `p3-paired`.
- The phone sends a frame the app can send, built from what it saw: devices. Mark `p3-listed`.
- Wait up to 10 s for the devices reply; mark `p3-listed-in`.
- The phone sends a frame the app can send, built from what it saw: revoke_device for UX second phone. Mark `p3-revoke`.
- The phone sends a frame the app can send, built from what it saw: revoke_device for the app's own iPhone (simulator lane; on the protocol lane, where there is none, a devices request). Mark `p3-revoke-app`.
- Wait 6 s.
- Screenshot `p3-revoked` (simulator lane).
- The phone sends a frame the app can send, built from what it saw: devices. Mark `p3-after`.
- Wait up to 10 s for the devices reply; mark `p3-after-in`.

**Preconditions** (any failure fails the scenario):

- the second phone paired and connected

**Rubric.**

| id | tells | lane | the user can tell | pass | fail |
| --- | --- | --- | --- | --- | --- |
| P3.1 | responsive | protocol | The removed phone learns it was removed, not just that the Mac is away. | its socket closes within 2 s with code 4001 | no close, a late one, or another code (the app would retry as if offline) |
| P3.2 | state | protocol | Its old token no longer opens a socket. | the second try after the close is refused | the removed phone gets back in |
| P3.3 | state | protocol | The paired list drops the removed phone and keeps this one. | devices after the revoke lacks UX second phone and lists the current phone | the removed phone still listed, or this phone gone |
| P3.4 | recover | simulator (p3-revoked) | A removed iPhone says it was removed and how to pair again, instead of reconnecting forever. | a pairing screen that says it was removed from the Mac | Reconnecting, an offline banner, or the old list |
